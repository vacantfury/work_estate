## What this repo is

An **installation package** (owner design 2026-08-03): the work-side seed of the owner's personal working conventions ("source system" is the name of his personal project ecosystem). The committed repo stays permanently generic; it is cloned onto a work device, where its unfold procedure detects the environment (work docs + device) and "unfolds" the seed into the adapted form that best serves him there — written to `local/`, never pushed back. It contains ONLY:

- the corpus: the parts of the source system discipline that work may use — task convention, session working style, engineering standards, generically useful skills;
- idea/direction notes about how to structure work-machine workflows;
- `UNFOLD.md`, the installer procedure.

**On a work machine, the first session's duty is to run `UNFOLD.md`.** Full model: `text_docs/design.md`.

## Scope boundary (load-bearing)

**This repo owns:** portable working discipline safe for a corporate device — e.g. the ordered-TODO task convention, engineering standards (uv, parameters-in-config-not-code), session discipline.

**Stays elsewhere, never enters this repo:** ALL of the owner's private content — profile/self-model, finances, immigration, people/contacts, message-channel access, his other systems' internals. Concretely: career strategy and employer-relationship records are the owner's own affair elsewhere, not here.

**The division, one line (owner-ratified 2026-08-06):** this installation = the job (day-to-day operations inside the employer boundary) · the employment's wider meaning for the owner's life is his own affair beyond it. The installation is self-contained; boundary discipline (`corpus/boundary-protocol.md`) binds: employer-confidential content stays in employer systems, and every record the owner keeps is written at meaning grain — employer-safe by construction.

## Hard content rules

1. **Employer-readable assumption:** anything committed may be read by the employer once the repo sits on a corp device. Write accordingly.
2. **One-way flow, generic in, nothing employer-derived out:** committed content is employer-generic convention only. Anything derived from employer docs, systems, code, or confidential context is NEVER committed or pushed here — it stays machine-local on the work device (`local/`, gitignored). This mirrors the owner's IP rule in both directions: nothing from work leaves the employer; nothing of the owner's private content enters this repo.
3. **No secrets of any kind** — no values, no secret-manager item names, no tokens, no placeholders that reveal private infrastructure.
4. **Not a bridge:** this repo is not a sync channel; work state never leaves the work device through it.

## Layout

- `CLAUDE.md` — this file: identity + hard rules, loaded by the owner's build sessions elsewhere and by work-side sessions if the sanctioned tooling reads it.
- `UNFOLD.md` — the installer: detect (work docs + device) → resolve the adaptation ledger → generate the adapted form into `local/`. Tooling-agnostic plain markdown — followable by any sanctioned agent, or manually.
- `corpus/` — the genome: the generic convention modules and portable skills the unfold selects from.
- `text_docs/design.md` — design record: the installation-package model, settled principles, the adaptation-points ledger. `text_docs/` also holds idea/direction notes.
- `knowledge/` — reference research digests (committed; same employer-readable discipline).
- `local/` — gitignored; the unfold's output home and the designated place for ALL work-machine-specific content. Nothing in it is ever committed.
- `TODO.md` — gitignored, per the owner's task standard (registered in his task system off this machine). On the work machine, the unfold seeds a local equivalent.
