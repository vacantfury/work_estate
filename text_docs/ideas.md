# Ideas & directions — work-machine workflows

Non-binding direction notes. The unfold and later work-side sessions consume these as orientation, never as law.

- **Instructions-layer mapping.** Whatever tooling A1 finds, the target shape is the same three tiers (always-loaded law · session board · on-demand state). Expected mappings: a full agent harness → memory file + skills directory; an instructions-consuming assistant → repo/workspace instructions file; nothing sanctioned → printed one-pager + checklists. The corpus is written so any of these is a formatting pass, not a rewrite.
- **Work-side head TODO.** One head list for work overall (in `local/state/`, or the work-managed location A4 picks), with per-repo tails if work spans several repos — same one-home/move-never-copy rule as the corpus convention.
- **Update channel.** If the seed's remote is reachable (A2 yes): occasional `git pull` + re-run of the unfold picks up corpus improvements. If not: the seed stays as installed, refreshed rarely via whatever sanctioned route exists. Either way the seed only ever flows inward.
- **Backflow discipline for generic improvements.** A genuinely employer-generic convention improvement invented during work-side use does NOT ride this repo back (the one-way rule has no exceptions and provenance would be tainted). If an idea matters enough, the user re-derives and re-authors it upstream, from their own understanding, on their own equipment. The repo never carries anything back.
- **Fold-away is expected, not failure.** On a locked-down device most of the corpus may fold away and only the reading-form conventions survive. That outcome is a success case of the design — the package is useful at every policy level.
- **Later candidates for the corpus** (add only if they prove portable in practice): a meeting-notes → action-items capture habit; a weekly review checklist over TODO + archive; a lightweight decision-record convention for work projects.
