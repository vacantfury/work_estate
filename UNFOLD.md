# UNFOLD — the installer

*Run on the work device, in the first session after cloning. Executable by any sanctioned capable agent — or manually by the user (degraded path at the end). This file is deliberately plain markdown with no dependency on any harness, language runtime, or feature: which AI tooling may execute it is itself a question it answers (A1).*

## Contract

- **Input:** this repo (read-only during the unfold), the work documents the user points at (AI-tooling policy, device/acceptable-use policy, engineering handbook if offered), and the device itself.
- **Output:** the unfold FOUNDS the work-side ESTATE — many projects, one per design-principle-19 roster row, at the root A4 chooses — plus the ledger and log in this clone's gitignored `local/`. The committed seed is never edited by the unfold, and nothing derived from employer docs, systems, or code is ever committed or pushed — the one-way flow rule (CLAUDE.md) is absolute.
- **Re-runnable:** generated instruction/skill layers are wiped and regenerated on each run; living project state (task files, boards, registers, records) is never touched by a re-run.

## What the unfold creates

- **The estate** (at the A4 root): a COPY of the seed's `skeleton/` tree — the shipped concrete form (`skeleton/README.md` draws it once) — adapted per the ledger. One directory per project: hub · store · finder · ties · worklog · compensation · career · health · risk · research (intake-§18-gated) · main-work, plus per-work-project homes created later at accept (principles 19–20) and the four gated infrastructure dirs copied only when their founding gates fire. Every project arrives with its instruction stub, `TODO.md` + `NOW.md` + `archive.md`, and its state files as ready templates; the unfold fills values, it never invents structure. Project homes are local git repos where device practice allows. The hub carries the estate registry (`hub/registry.yaml`) — every project, its home, its state files, its edges; corpus references to `local/state/<file>` resolve to the owning project's state home via this registry.
- **In this clone's `local/` (gitignored):** `local/ledger.md` — the resolved A1–A8 answers, each with its deciding evidence, dated; re-runs append a new dated section, keeping history — and the unfold log.

## Phase 0 — precondition gate

1. Confirm the device policy permits a personal-convention repo on this machine (this is A3, resolved first because everything else depends on it). Evidence: the device/acceptable-use policy, or an explicit answer from the user after they check.
2. If the answer is no or remains unclear → **STOP**: delete the clone, record nothing on the device. The corpus still serves in reading form elsewhere.

## Phase 1 — detect

Gather evidence; note everything observed (it feeds Phase 2).

1. **Work docs:** read the documents the user supplies — AI-tooling policy (what agents/endpoints/tools are sanctioned), device policy, engineering standards if offered. Extract only what the ledger needs; quote policy minimally.
2. **Device inspection (read-only):** what AI/agent tooling is installed or available (internal tooling, editor agents, CLIs); what runtimes exist (`git`, `python`, `uv` versions); what backup/sync mechanisms the employer provides (managed folder sync, work-hosted git, device backup — feeds A6); whether the seed's remote is reachable (a credential-free read-only check, e.g. `git ls-remote` on this repo's public URL — the repo is public so this check needs no credential; the user's own credentials land on the device only later, per the amended credential rule in `corpus/boundary-protocol.md` and the setup order in `corpus/research-infrastructure.md`, never to make this check pass).
3. **Work stack and real conventions:** which languages/build systems dominate the repos actually worked on, and the conventions actually practiced in them — read the code and recent merged PRs, not only any written guide; the real house style may be documented nowhere (design principle 10). On the first run this may be unknown — mark it deferred; it refines A5 on a later re-run.
4. **Axis-2 assumptions:** walk `knowledge/week1-intake.md` (the pre-start assumptions ledger). Record confirm/refute/refine per entry in `local/` — some entries resolve from the same docs/inspection as steps 1–2; the rest become the user's week-1 questions. Results feed A5 and calibrate the provisional `corpus/role-playbook.md` module.

## Phase 2 — resolve the ledger

Answer A1–A8 in `local/ledger.md`, each with the one evidence line that decides it. An unanswerable question is recorded as **unresolved** with what's missing — never guessed.

- **A1 — sanctioned AI tooling.** Decides what executes future sessions and the format of the generated instructions layer — and, with the intake §17 answers (token budget, unattended-run policy, reachable surfaces), the work engine's queue mode and budget knob (`corpus/work-engine.md`). Outcome classes: a full agent harness · an instructions-consuming assistant · none (→ degraded path).
- **A2 — remote reachability.** Decides the update channel: reachable → versioned delta updates (§Update) pick up seed improvements; not reachable → the seed is refreshed rarely, by whatever sanctioned transfer route exists, or not at all.
- **A3 — personal-repo policy.** Already gated Phase 0; record the evidence here.
- **A4 — the estate root and project-home form.** Where the work-side estate lives (a work-projects directory in the user's device home, or a work-managed location if policy or practice prefers it) and what form project homes take (plain dirs · local git repos · work-hosted git). Default: a projects directory with each project a local git repo. Record the chosen root in the ledger; the estate never pushes to the seed's remote.
- **A5 — applicable convention/skill subset.** Per corpus module and per portable-skills entry: **adopt / adapt / fold away**, one-line reason each. What is folded away stays in the corpus, available to later re-runs.
- **A6 — backup of the work-side estate.** The estate never pushes to the seed's remote, so it is single-copy until a route is chosen. Decide the backup process ONLY from what Phase 1 found: the work docs (what storage the policy sanctions for work-adjacent personal notes) and the tools actually available on the device (employer-managed folder sync, work-hosted git, device backup). Never a personal cloud or the personal remote — one-way flow is absolute. If A4 rooted the estate in a work-managed location, backup may already be inherited — record that as the answer. Nothing suitable found → record **unresolved** and note that the estate is consciously single-copy until re-run.
- **A7 — the storage engine.** The best sanctioned store for the estate's typed data (`corpus/store.md`): an embedded database where a runtime exists, the tooling's native memory otherwise; markdown-with-shape is the bootstrap form.
- **A8 — the access rosters.** Which surfaces the tooling can actually reach, in which access mode — TWO rosters: the finder's knowledge sources (`corpus/finder.md`) and the ties bus's traffic channels, mail · chat · calendar (`corpus/ties.md`).

## Phase 3 — found the estate (copy-then-adapt)

From the resolved ledger, found the work-side estate at the A4 root (design principle 19). **The layout is never derived: the seed ships it as `skeleton/` (principle 30), and this phase copies it, deletes what does not apply, and fills the resolved values.** Founding rules: an existing project or state file is NEVER overwritten — re-runs regenerate instruction/skill layers only.

0. **Copy the skeleton.** Copy `skeleton/` to the A4 root, excluding: `_clone/` (its `ledger.md` template seeds THIS clone's gitignored `local/ledger.md` in Phase 2) · the four gated infrastructure dirs `llm_utils/` `devices/` `autoflow/` `auto_research/` (each copies whole when its founding gate fires) · `research/` unless intake §18 cleared personal-stack presence. Then: delete the files of every A5 fold-away (each deletion recorded in the ledger — the corpus keeps the fold-away for later re-runs); strip each instantiated file's `skeleton template` header line and add the provenance header (§Update step 3); make each project home a local git repo where device practice allows.
1. **Fill the hub** — the estate's steward project:
   - **Estate registry:** the copied `hub/registry.yaml` ships every default row — fill its placeholders (home paths at the A4 root, the A7 engine field) and delete rows the copy excluded. No unregistered projects; corpus references to `local/state/<file>` resolve to the owning project's state home via this registry. **The seed clone itself gets one row** (kind: seed — the estate's one evolving external dependency, never a work project): clone path · installed version (the clone's `HEAD`, tag name where one matches) · update-channel state (the A2 outcome) · last checked · last applied. The hub traces seed updates through this row; day-to-day work never happens in the clone. **Every row also declares its EDGES** — `consumes:` (infrastructure seams) · `feeds:` (where outputs flow) — so the registry IS the estate's structure graph, renderable on ask; crossings obey the crossing protocol (`corpus/estate-structure.md`).
   - **Instructions layer (tier 1):** the always-loaded instructions file in the sanctioned tooling's native format — an agent-memory file, a repo instructions file, or (no tooling) a printable conventions one-pager. Content: the adopted estate-wide law (A5 subset of the craft/standards modules), law only — no changing facts. Per-project instruction files state each project's own scope and cite the hub's law, never copy it.
   - **Task head:** the hub's `TODO.md` is the estate head — the user's ordered next actions across projects; other projects' TODOs are tails. Where A7 provided a store engine, found every task list STORE-FIRST per the store-backed form (`corpus/task-convention.md`): store as truth, `TODO.md` a generated view, writes through the task verbs; a degraded install keeps flip-ready markdown and flips at the first update pass that finds an engine.
   - **Agent-jobs engine:** the copied `agent-jobs.yaml` ships the schema and drafted defaults (`corpus/work-engine.md`); tune priorities/cadences and set the queue mode from A1 + intake §17 (scheduled agents · session-opening sweep · degraded checklists), cutting jobs whose lane folded away. Each job writes its OWNING project's state.
   - **Footprint register:** the copied register is ready; back-fill a line for anything personal already present on the machine (this clone itself needs no line while the repo is public and credential-free; the first of the user's credentials or sign-ins does).
   - **Self-model:** fill `self.md` (sections shipped; `corpus/self-model.md`) from the intake answers already gathered (§8–§10) plus what the user states; work grain only.
   - **Decision log:** `decisions.md` is copied ready; the deliberation procedure itself materializes in the skills layer (step 2) as a hub skill.
2. **Skills layer:** materialize each adopted portable-skills entry in the tooling's skill/instructions format, homed with the project it serves (estate-wide ones in the hub); with no tooling, keep them as printed checklists in the hub. The people/message/meeting flow (`corpus/ties.md`) and the writer's craft lane (`corpus/communication-craft.md`) materialize here — procedures and engine jobs, the craft lane's state under the hub's engine: there is NO separate communication project (meeting outcomes live in the worklog; person state lives on the employer's own surfaces — design principle 29).
3. **Fill the infrastructure trio:** the store (`corpus/store.md`) — record the A7 engine in `store/schemas/schemas.yaml` and the registry row (markdown-with-shape bootstrap if none); the finder (`corpus/finder.md`) — fill `finder/sources.md` from A8; the ties bus (`corpus/ties.md`) — fill the channel table in `ties/routing.md` from A8 (people read live off the employer's directory and threads — no store to seed). All three are registry rows of kind infrastructure; every later project consumes them.
4. **Worklog:** `worklog.md` + `timelog.md` + the reports dir are copied ready (`corpus/work-record.md` + `corpus/work-report.md`) (expected core-adopt at every policy outcome; the seed-refresh line in `corpus/boundary-protocol.md` is the one piece depending on A2). The PUBLIC view's home is an intake question (`knowledge/week1-intake.md` §15) — the staging file `worklog-public.md` serves until it resolves; once a team surface is named, render there and retire the staging file.
5. **Compensation:** fill the copied register's first entries from the offer packet's pay components (base, bonus target, stock award + vest schedule, sign-on terms; `corpus/compensation.md`); then catalog discovery on the employer's benefits/program portals (intake §19) — at a fresh employment, the new-hire enrollment window is read off the portal FIRST (short window, usually irreversible once closed).
6. **Career:** shape the copied `review.md` + `promotion.md` to the review-instrument and leveling answers intake §20 has already surfaced (`corpus/career.md`); `growth.md` + `themes.md` + `company.md` are copied ready; the company-watch capture job ships in the copied `agent-jobs.yaml` — its signals type into the store, themes and the reward map feed `themes.md`.
7. **Health:** the tracker is copied ready (`corpus/health-guard.md`); wire the guard's clock from what Phase 1 found — the best reminder mechanism the device and sanctioned tooling offer (calendar blocks, OS/assistant break reminders, the agent's own surface; degraded path: phone timers + the printed moment table).
8. **Risk:** fill the copied `risks.md` opening entries from the module's seed premortems, adapted to what intake discovered (`corpus/risk-register.md`).
9. **Research** (copied only where intake §18 cleared any personal-stack presence): the satellite registry is ready (`corpus/research-infrastructure.md`); clones and credentials follow that module's setup order, each landing a footprint-register line.
10. **Main-work — the manager of all product work:** pre-fill the copied portfolio board `projects.md` with candidates from the intake's project-landscape questions (`knowledge/week1-intake.md` §12; `corpus/project-pipeline.md`). Per-project homes are founded UNDER main-work on demand at accept by copying `main-work/_template/` (`corpus/project-home.md`, via the project-founding procedure in `corpus/portable-skills.md`; each registered in the estate registry) — never pre-seeded.
11. **Personal-residue sweep.** The seed is written to carry no personal content (hard content rules, `CLAUDE.md`), but a slip is possible. Sweep the clone's committed content AND everything just generated for residue violating those rules — personal names, account handles, personal contact details, references to any system outside this tool. On a hit: delete it from the local clone and every generated layer the same session, and add a hub TODO line for the user to relay the finding upstream so the seed fixes it at source (until that fix ships, a later pull may re-deliver the content — the sweep re-fires at every update apply).
12. **Log:** write the unfold log in this clone's `local/` — date, ledger summary, the estate registry as founded, what was folded away.
13. **Report to the user:** the ledger answers, the estate as founded (each project + its home), and the single next action (typically: wire the hub's instructions file into the sanctioned tool, exact steps stated).

## Update

A seed update is applied as a DELTA against the version the estate was derived from; the full unfold never re-runs for a seed change. The clone's own git position is the installed-version marker: `HEAD` is the seed state the estate was last derived from, and moving it (the `git pull` at the end of an update) is what marks the update complete. Seed versions are SemVer tags; `CHANGELOG.md` is the update package's manifest — each entry names the changed modules and the derived layers they affect.

1. **Check (read-only; on the user's ask, or at most once per session opening).** `git fetch origin`, then `git log --oneline HEAD..origin/main` and `git diff --stat HEAD origin/main -- corpus/ UNFOLD.md knowledge/`; read the `CHANGELOG.md` entries above the installed version. Report and stop: versions and modules changed, which generated layers are affected, confirmation that living project state is untouched. Record the check on the hub registry's seed row (last checked, newest version seen) — pending updates then surface through the hub's ordinary attention view, never as their own ceremony. Nothing is applied without the user's go.
2. **Apply (delta only).** For each changed module, consult the existing ledger: adopt/adapt rows regenerate their derived layers from the new module text using the recorded answers — nothing already answered is re-asked; fold-away rows are noted and skipped; a module new since the installed version gets one fresh A5 row; a genuinely new ledger question is asked once. Then run the personal-residue sweep (Phase 3 step 11) over the pulled delta and anything regenerated from it — a slip in the seed is deleted locally the same session and flagged on the hub TODO for upstream fix.
3. **Never clobber a local edit.** Before overwriting a generated file, check whether it was edited since generation (via its provenance header, or by regenerating from the module text at the current `HEAD` and comparing; for skeleton-instantiated files, diff against the template at the installed version). Unedited → overwrite. Edited → show the diff and merge the seed change in, keeping the local adaptation. Every file (re)generated from this mode's first run onward carries one provenance header line: `generated from work_estate <version> · module <path> · A5: <decision>` (skeleton-instantiated files name their template path as the module). (Headers written before 3.4.1 carry the repo's former name — same repo, still valid.) **Skeleton adoption on an estate installed pre-v6.0.0:** the update's apply step offers a one-time conformance pass — add missing template files, report layout divergences — and NEVER moves or rewrites living state without the user's word per file.
4. **Record and advance the marker.** Append a dated update section to `local/ledger.md` (version from → to, layers regenerated, merges made), update the hub registry's seed row (installed version, last applied), then `git pull` so `HEAD` records the new installed version. Where the engine runs scheduled jobs, the check step MAY register as a low-cadence job (`agent-jobs.yaml`; A2-gated); apply always waits for the user.

Living project state (task files, boards, registers, records) and the estate registry's existing entries are never touched by an update. A full re-run from Phase 1 remains the instrument for WORK-side change (policy or tooling shifts at the employer); seed changes always ride this update mode. Bootstrap: an estate installed before versioning existed has no provenance headers and no seed row — treat the clone's current `HEAD` as the installed baseline, and add the hub registry's seed row on the first update run; headers appear as layers are first regenerated.

Post-install, the clone's ONLY role is this update channel: day-to-day work happens in the estate projects, never in the clone (design principle 19). If the update channel goes unused (A2 unreachable), the clone is deletable without loss.

## Degraded manual path (no AI tooling sanctioned, or policy cannot carry a multi-project estate)

The single-clone fallback — used only when the estate form genuinely cannot exist here (design principle 19), never as a convenience default:

1. Read the corpus modules; adopt them as personal working conventions in reading form.
2. Copy what serves from `skeleton/` into this clone's `local/state/` (at minimum the hub's `TODO.md` and `NOW.md` templates); maintain per `corpus/task-convention.md`. Even with no agent, the skeleton is directly usable by hand — that is why it ships as files.
3. Use the portable-skills entries as printed checklists.
4. Re-check the tooling policy occasionally; if an agent later becomes sanctioned, run the full unfold and found the estate.
